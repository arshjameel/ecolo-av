Ben, 24 Oct: "Do we have a mathematical model for the car now for the ego? ... a matrix control thing ... Maybe second order system". Now we do. This page writes the car the way SYSC 3600 (Systems and Simulation) would: differential equations, Laplace, transfer functions, state space, poles, step responses and Bode margins.

New to this, or rusty? Start with Learn: state space: the whole process, from a free-body diagram to a simulator, one step at a time.

The short version

  • Three parts: speed (second order, with the spine's PI around it), steering (second order), and the path errors (state space, 3 states).
  • Today's numbers are guesses from vehicle.yaml. The car day's actuator tests measure each one; pixi run vehicle-model --set throttle_lag=0.25 redoes it all.
  • The spine's speed loop is slow: it settles in about 13 s, and overshoots 15%. Delays don't matter to it (62° of phase margin even in the worst case).
  • The smooth profile fixes the overshoot (TODO 27): a setpoint weight. 0% overshoot, settles in 8 s, and holds up when the throttle guess is 5x off. Not the default: it waits for the stands (Tuning the speed loop).
  • The lateral loop is where delays matter: 52° of phase margin with none, 45° with today's 84 ms, 31° with the worst case (259 ms) at 1 m/s.
  • Gazebo's car steers as vehicle.yaml says, within 22 ms (25 Oct; it was 0.11 s late: an extra lag in Gazebo's own steering, now fixed: section 6).
  • Nothing here drives the car. It is for tuning, checking, and the report.

works the maths and its 35 tests: 30 cases in test_vehicle_model.py, 5 in tools/tests/test_vehicle_model_tool.py (24 Oct, Ben's Mac; the speed loop's 25 Oct). needs you the car day's numbers.

1. Speed

The differential equations

The throttle reaches its level with a first-order lag:

τt · du_a/dt + u_a = u

The car speeds up in proportion to the throttle, and drag slows it in proportion to its speed:

dv/dt = a_max · u_a − d · v

Divide by d. It's the textbook first-order form:

τv · dv/dt + v = K · u_a        τv = 1/d = 10 s,   K = a_max/d = 15 m/s

Laplace and transfer functions

V(s) / U_a(s) = K / (τv s + 1)                    the car
U_a(s) / U(s) = 1 / (τt s + 1)                    the throttle
P(s) = K / ((τv s + 1)(τt s + 1))                 throttle command to speed

Poles: s = −1/τv = −0.1 (the car: slow) and s = −1/τt = −10 (the throttle: fast). Alone, the car reaches 63 % of its final speed after τv = 10 s.

State space

x = [v, u_a]

x' = A x + B u        A = [ −d    a_max ]      B = [  0   ]
                          [  0   −1/τt  ]          [ 1/τt ]
y  = C x              C = [ 1  0 ]

The spine's speed loop around it

firmware/spine/crates/spine-core/src/speed_loop.rs, while it uses the throttle:

e = v_set − v
throttle = kp·e + ki·∫e dt          C(s) = kp + ki/s = (kp s + ki)/s

The closed loop, T(s) = C P / (1 + C P). Leave out the fast throttle lag first: the characteristic equation is

s² + (d + a_max·kp) s + a_max·ki = 0
s² + 0.55 s + 0.15 = 0
s = −0.275 ± 0.273j          ωn = 0.39 rad/s,   ζ = 0.71
Loop Poles (1/s) Rise (10-90 %) Overshoot Settles (2 %)
the car alone −0.1 22 s 0 39 s
spine PI, no throttle lag −0.275 ± 0.273j 2.7 s 14 % 12.9 s

What the poles mean for the car:

  • The pair at −0.28 ± 0.28j: the car reaches a new speed in about 3 s, overshoots by 15 %, and settles in 13 s. Slow, but smooth.
  • The overshoot is more than ζ = 0.71 alone gives (about 4 %): the PI adds a zero at −ki/kp = −0.33, near the poles. The ramped set speed doesn't hide it: Gazebo's car reversed at 0.57 m/s for ego's 0.5 (TODO 27). The fix: Tuning the speed loop.
  • The pole at −9.5 is the throttle: 30 times faster, so it hardly matters.

2. Steering

The Jrk G2 turns the steering motor toward its target at up to r = 0.8 rad/s (a rate limit: nonlinear). The linkage follows with a lag τl = 0.1 s.

Linearising the rate limit. For a step of size A, the rate limit takes A/r, and its average delay is A/(2r). A first-order lag with that delay has

τm = A / (2r) = 0.1 / (2 × 0.8) = 0.0625 s        (for A = 0.1 rad, a lane-keeping step)

Two lags in a row make a second-order system:

G_s(s) = 1 / ((τm s + 1)(τl s + 1))
       = ωn² / (s² + 2ζωn s + ωn²)

ωn = 1 / √(τm·τl)                 = 12.6 rad/s
ζ  = (τm + τl) / (2·√(τm·τl))     = 1.03
ωn ζ Rise Overshoot Settles
12.6 rad/s 1.03 (just overdamped) 0.28 s 0 0.49 s

What it means: the steering is about 10 times faster than the path loop (ωn 12.6 vs about 1 rad/s), so the path loop sees it as a small delay, τs = 2ζ/ωn = 0.16 s.

What's a guess: all of it. Two real lags can never overshoot (ζ ≥ 1). If the Jrk's own position loop overshoots on the car, read the overshoot off test 3.11's step, and --set steer_overshoot=0.1 sets ζ from the textbook formula:

overshoot = exp(−ζπ / √(1 − ζ²))        ζ = −ln(OS) / √(π² + ln²(OS))

Left out: the rate limit itself (big steps take A/r: full lock from centre takes 0.6 s), the deadband (0.005 rad), and the software's own rate limits before it (ego and the spine: 0.6 rad/s, slower than the motor).

3. The path: lateral state space

The kinematic bicycle

The same model as ego and MPPI, about the rear axle (base_link), the path along x:

x' = v · cos θ
y' = v · sin θ
θ' = v · tan δ / L

Linearised about driving straight

Small angles: sin θ ≈ θ, tan δ ≈ δ. With the steering as one lag τs:

e_y' = v · e_θ
e_θ' = (v / L) · δ
δ'   = (δcmd − δ) / τs
x = [e_y, e_θ, δ],   u = δcmd

     [ 0   v    0     ]        [  0   ]
A =  [ 0   0   v/L    ]    B = [  0   ]
     [ 0   0  −1/τs   ]        [ 1/τs ]

At 1 m/s, today: A = [[0, 1, 0], [0, 0, 0.637], [0, 0, −6.15]], B = [0, 0, 6.15]ᵀ. lateral(v, steering_order=2) gives the 4-state version with the second-order steering (δ' as a state).

Eigenvalues: 0, 0 and −1/τs = −6.15, at every speed. The two at 0 are a double integrator: steer, and the heading changes; the heading, and the car drifts sideways. Left alone, nothing pulls the car back. Speed changes B's reach (v and v/L), not the eigenvalues; in reverse, v < 0 flips the signs.

The test checks A against a finite-difference Jacobian of the nonlinear bicycle.

Closing the loop: pure pursuit

These margins are for Regulated Pure Pursuit (controller:=rpp). MPPI, the default since 22 Oct (Path followers), isn't modelled here.

Regulated Pure Pursuit steers for the curvature 2 sin α / ld toward a point ld ahead on the path. For small errors:

δcmd = −(2L / ld²) · e_y − (2L / ld) · e_θ          u = −K x

With no steering lag, the closed loop is

s² + (2v / ld) s + 2v² / ld² = 0        ωn = √2 · v / ld,    ζ = 0.707 at every speed

RPP's lookahead grows with speed (ld = 1.5 s × v, from 1.5 to 4 m), so v / ld stays the same from 1 to 2.7 m/s: the car corrects in the same time at any of those speeds.

An actuator's dead time is part of the car, so it adds to every case, "none" too: speed_delay(case) adds throttle_dead_time, lateral_delay(case) adds steer_dead_time. Both are 0 until the car day, so the numbers below don't change yet.

The lateral delays are lane keeping's, by camera. Nav2 following a path from the EKF has no camera in the loop (its own delay is the EKF's), so its margins sit between "none" and "typical". The heartbeat isn't a delay in normal driving: it is the most a command may lag before the brakes take over, so the worst case counts all of it.

Padé. A delay e^(−sT) isn't a ratio of polynomials. Padé replaces it with one, so poles still make sense:

e^(−sT) ≈ (1 − sT/2 + (sT)²/12) / (1 + sT/2 + (sT)²/12)        (second order)

The margins below use the exact delay (it only subtracts ωT from the phase); pade() is there for pole maps and for simulation.

5. Discrete time: as the computers run it

The spine runs every 10 ms; the controllers every 50 ms. scipy.signal.cont2discrete with a zero-order hold (the command is held until the next one) gives

x[k+1] = Φ x[k] + Γ u[k]        Φ = e^(AT),   Γ = ∫₀ᵀ e^(Aτ) dτ · B
Loop Period Largest |z| e^(sT) of the continuous poles
speed (the spine's own update: integral first, then kp·e + I) 10 ms 0.99720 0.99720
lateral at 1 m/s, the command one cycle late 50 ms 0.960 0.963
lateral at 3 m/s, the command one cycle late 50 ms 0.954 0.958

All inside the unit circle: stable. At 10 ms the spine is effectively continuous. The tests check the discrete model against the continuous one at every sample, and the discrete speed loop against the spine's own code, line by line.

What it's for

Tuning the speed loop

  • The firmware's defaults don't change. The throttle's strength is a guess that two sources disagree on by 5x (TODO 52b): full throttle holds 15 m/s by the drag guess, 3 m/s by the ESP32's open loop. The real gains come from the stands, after the throttle tests.

Why it overshoots: the PI's zero

Not windup. The throttle is never pinned on the way to 0.5 m/s (it peaks at 0.15), so clamping changes nothing (the table below). The cause is the PI's zero:

T(s) = P (kp s + ki) / (s (1 + C P))       zero at −ki/kp = −0.33,  slow poles −0.28 ± 0.28j

The fix is a setpoint weight b: the P term sees only b × the set speed.

throttle = kp·(b·r − v) + ki·∫(r − v) dt
T(s) = P (b kp s + ki) / (s (1 + C P))     zero at −ki/(b kp);  the poles don't move

The poles, the margins and how the car rejects a hill don't depend on b. Only the response to a new set speed does.

  • The price: kp 1.0 makes the throttle 3x more sensitive to a noisy wheel speed. Watch /vehicle/throttle for jitter on the stands.

Pole placement, after the car day

Match the closed loop (no throttle lag) to the poles you want:

s² + (d + a_max·kp) s + a_max·ki  =  s² + 2ζωn s + ωn²
kp = (2ζωn − d) / a_max
ki = ωn² / a_max

With the measured a_max and drag (TODO 52b), place the poles real (ζ ≥ 1), then set b so the zero −ki/(b kp) sits just past the slow pole. smooth is that recipe, done on today's guesses: it is a starting point for the stands, not the answer.
