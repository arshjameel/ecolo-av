Train in PyTorch; run the model as ONNX, from Rust, with ONNX Runtime (Ben, 16 Nov, TODO 243). First on a Mac through Core ML; on the Orin later through TensorRT.

Three models, end to end, each a challenger beside the default:

Model From Rust Switch
the RF-DETR Nano detector (the stop signs) the node aav_detector_rs detector_impl:=rust
the diffusion planner (its model; the guard stays) the worker aav_diffusion_rs diffusion_impl:=rust
the learned lane finder (TODO 262b, ours, trained here) the node aav_lane_finder_learned lane_finder_impl:=learned

Ben, 19 Nov: "if it works on a mac it should work there correct?" Mostly: one .onnx per model; what Core ML runs whole is the best guess of what TensorRT will. So every model is checked here first: pixi run measure onnx.

The diffusion planner from Rust

Only the model moved: aav_diffusion_rs's diffusion_worker speaks the Python worker's pipe, so the node, its window, its guard (G1-G8) and the lattice's fallback are unchanged. diffusion_impl:=rust diffusion_provider:=auto.

ms a plan (16 paths, 10 steps) Paths against the CPU's
Python worker, ONNX Runtime, CPU (today's default) 63-87 the reference
PyTorch (mps) 22.9 same (0.000 m)
Rust, Core ML (all 2,178 nodes, one piece) 9.7 same (6e-7 in the window's units)

To get there the export changed (19 Nov), the same numbers: 16 samples fixed (Core ML can't build an open number; another number runs in batches), and no ScatterND, Expand, Flatten, 1D AveragePool or Resize (the 0.3 export went to Core ML in 376 pieces, slower than the CPU). The model was trained again on this Mac (pixi run diffusion data, train --epochs 40, 57 min): 58.6 % of samples pass the guard, 84.7 % of plans have one (0.3's: 63 %, 87 %).

Found on the way: the node asked for the global costmap as "transient local"; ours (Rust, since 16 Nov) sends it "volatile", so it never arrived and every plan was the lattice's. Fixed: the node reads it volatile. A first look after the fix (one tour, cut short): 2 of 4 plans a leg from the model. Ravensim scoring deferred (Ben, 19 Nov: algorithm testing comes after the ports): pixi run measure controllers --planners diffusion diffusion_rs --reversing --tours lot --runs 2.

FP16

tools/export_model.py --format onnx --fp16 (the detector; ONNX Runtime's converter) and pixi run diffusion export --fp16 (the diffusion planner) write *_fp16.onnx: half precision inside, float32 in and out.

Core ML's units detector FP32 detector FP16 diffusion FP32 diffusion FP16 lanes FP32 lanes FP16
all (what we ask) 9.7 9.7 9.7 9.5 2.5 1.2
CPU and GPU 9.8 8.9 9.7 9.4 2.4 2.1
CPU and Neural Engine 28.8 9.6 21.7 27.2 4.8 1.2
CPU only 28.8 19.8 21.6 18.2 4.7 3.0
  • The Neural Engine runs the FP16 detector (9.6 ms against the CPU's 19.8) but not the FP32 one, nor the diffusion planner (no faster than the CPU).
  • The Neural Engine runs the FP16 lane finder too, whole: 1.2 ms, half the GPU's FP32 time, within 0.04 px; with all units Core ML picks it itself.
  • On this Mac FP16 buys nothing for the detector and the planner: with all units Core ML picks the GPU, 9-10 ms either way.
  • The detector's FP16 loses boxes on Core ML (fine on the CPU): keep FP32 on the Mac. On the Orin, TensorRT makes its own FP16 from the FP32 file (trt_fp16_enable), so the FP16 files are only for checking.

ort's default adds Core ML

ort 2.0.0-rc.15, on any Mac, quietly adds Core ML in its older, half-precision format, even to a "CPU" session: boxes then moved by up to 2 % (IoU 0.978). We switch that off (AutoDevicePolicy::PreferCPU): only the provider asked for runs.

Untested: the Orin

What State
The Rust with --features tensorrt (and cuda): onnx-session, the detector, the diffusion worker untested compiles (cargo clippy) on the Mac; never linked or run
An ONNX Runtime with TensorRT for the Orin untested ort downloads pyke's ARM Linux build with CUDA 13 and TensorRT: it may fit JetPack 7.2 (CUDA 13, Q24), not JetPack 6 (CUDA 12)
The same code picks TensorRT untested ready: device:=tensorrt (detector), diffusion_provider:=tensorrt (Rust worker); auto picks it when the build has it and no Core ML
Its engine cache untested ready: FP16 on, the engine and the timing cache kept beside the model: models/<model>.cache/tensorrt/. The first start builds them (minutes); a new TensorRT (a JetPack upgrade) builds them again: delete the folder
What TensorRT will take a guess from Core ML: the diffusion model whole (one piece, plain ops), the detector all but 6 shape steps
