Every computer runs ROS 2 Jazzy. On the car's computers that means Ubuntu 24.04 with the official packages. On a Mac or any other Linux, use Pixi: see Run it.

Which computer gets Jazzy how

Computer OS Jazzy from
Jetson AGX Orin JetPack 7.2 (Ubuntu 24.04) apt. JetPack 6 is Ubuntu 22.04, so reflash first, after a backup. To try it before then: Pixi, below.
Raspberry Pi 4 or 5 Ubuntu 24.04 Server (arm64) apt; or Pixi on today's OS, below
Linux laptop Ubuntu 24.04 apt, or Pixi
Mac macOS 14 or newer Pixi: Your Mac
oirp-spss AlmaLinux 9 Pixi, with no admin rights
Windows Windows 10 or 11 WSL2 with Ubuntu 24.04

Every computer on one ROS network must run the same release: Humble and Jazzy don't mix.

Ubuntu 24.04: install Jazzy

The official steps, from docs.ros.org ("Ubuntu (deb packages)"):

sudo apt install software-properties-common curl
sudo add-apt-repository universe
export ROS_APT_SOURCE_VERSION=$(curl -s https://api.github.com/repos/ros-infrastructure/ros-apt-source/releases/latest | grep -F "tag_name" | awk -F'"' '{print $4}')
curl -L -o /tmp/ros2-apt-source.deb "https://github.com/ros-infrastructure/ros-apt-source/releases/download/${ROS_APT_SOURCE_VERSION}/ros2-apt-source_${ROS_APT_SOURCE_VERSION}.$(. /etc/os-release && echo ${UBUNTU_CODENAME:-${VERSION_CODENAME}})_all.deb"
sudo dpkg -i /tmp/ros2-apt-source.deb
sudo apt update && sudo apt full-upgrade -y
sudo apt install ros-jazzy-desktop ros-dev-tools     # ros-jazzy-ros-base on the Pis and the Orin
sudo rosdep init && rosdep update

Add source /opt/ros/jazzy/setup.bash to ~/.bashrc. To check it, run ros2 run demo_nodes_cpp talker in one terminal and ros2 run demo_nodes_py listener in another.

Ubuntu: build this workspace

source /opt/ros/jazzy/setup.bash
rosdep install --from-paths ros --ignore-src -y    # every stock package we use
colcon build --symlink-install
source install/setup.bash                          # in every new terminal
  • --symlink-install links the Python files and configs instead of copying them, so an edit only needs a relaunch. C++ and message changes still need a rebuild.
  • colcon build --packages-select aav_ego builds just one package.
  • After switching branches, delete build/, install/ and log/, and rebuild.

Networking: many computers, one ROS graph

ROS 2 has no master. Nodes find each other by multicast on the local network.

# Rule Why
1 The same ROS_DOMAIN_ID in every machine's ~/.bashrc: ours is 42 (0–101 is safe on Linux; Fast DDS breaks above 232) the 2025-26 dashboard used 10 and its UI used 0, so they never met
2 One network that allows multicast, such as the car's own router campus WiFi often blocks it; then list the computers in ROS_STATIC_PEERS
3 Keep ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET set it to LOCALHOST to keep a laptop's experiments off the car
4 One middleware everywhere: Cyclone DDS (Ben, 23 Oct), set by Pixi different middlewares may not talk to each other; Fast DDS delivered messages late (Your Mac)
5 Clocks in sync: chrony, with the Orin as the time server TF and the EKFs reject messages from a wrong clock
6 Virtual machines on bridged networking, not NAT so the VM gets its own address on the car's network

ros2 doctor --report and ros2 multicast send / receive diagnose most problems.

On the car: what runs where

As the car is wired today (Ben, 23 Oct; the hardware lead confirms), the Motor Pi drives the ESP32, and the CAN bus goes to the Orin with the wheel sensors on it (Today's wiring). car.launch.py actuators:=uart (the default) is that; actuators:=can is the KEFC plan's CAN spine. The files in ros/bringup/aav_bringup/config/machines/ say what runs where:

Machine file Runs
orin.yaml description, mux, ego, scripted, drive_to_point, the IMU and GPS drivers, the roof lidar (Velodyne), localization, Nav2, Foxglove; the two front camera streams (camera_stream, RF-DETR inside each) and the stop-sign watcher; the CAN bus (spine_bridge role:=sensors: the wheels)
motor_pi.yaml legacy_uart_bridge: the ESP32 is wired to it. The 2025-26 UDP encoder (encoder_udp) is off: the wheels are on CAN now
laptop.yaml the joystick, on the safety driver's laptop, and its own detector (object_detector_laptop, RF-DETR Nano) on the compressed pictures: pixi run -e ml car laptop
all.yaml everything on one computer, for the bench. Its detector is object_detector_all

On each computer, run ros2 launch aav_bringup car.launch.py machine:=<its file>, or pixi run car <its file> with Pixi.

The first hardware test

Wheels off the ground, the e-stop in reach, and a low speed limit in ego.yaml. Check that positive steering turns left, that the throttle goes the right way, and that the car stops when you release the deadman and when you kill the bridge. Today's firmware fails the last one: see Firmware.

The parts

Each machine file turns parts on (true) or off. A TODO marks a part waiting for its hardware: the cameras (Q22), the radar, or which USB port a device is on.

Part Starts
description the car's frames: robot_state_publisher
mux, ego twist_mux, then ego
teleop the joystick, and its e-stop button
scripted, drive_to_point the scripted driver; the point driver (A to B)
imu, gps, radar, battery the sensor drivers, on the computer each is plugged into
lidar the roof Velodyne VLP-16, through the stock velodyne driver (it sends to the Jetson only)
camera the front camera: usb_cam, Linux only
camera_stream the front cameras' H.264 streams from the camera Pi, one camera_stream_<camera> each, with the detector inside; the sensor watchdog watches them (camera pipeline). On in orin.yaml
detector the object detector (RF-DETR Nano, or YOLO), as object_detector_<machine>, with the model the file names (Models). Not for a camera camera_stream streams
stop_signs the stop-sign watcher: one per car, next to the mux
radar_clusters the radar's clustering
camera_obstacles the detectors' boxes as points on the road, for Nav2's costmap (Costmaps)
localization, navigation the two EKFs and navsat_transform; Nav2. Its costmap reads the radar and camera_obstacles parts on the same computer, and collision_monitor comes with the radar
spine the CAN bus (Linux only): with actuators:=uart, the wheel sensors only (spine_bridge role:=sensors, no CAN sender); with actuators:=can, the CAN spine backend
legacy_uart, legacy_encoder today's backend, the ESP32 over UART (not with actuators:=can); the 2025-26 UDP wheel encoder (never beside spine)
foxglove foxglove_bridge, on port 8765: watch only, the WiFi topic list (Watch from a laptop)

A part that can't run on that computer (no PyTorch, no model file, no usb_cam) is skipped with a warning, and the rest starts.

The arguments

They win over the machine file. With Pixi, put them after --: pixi run car orin -- gps:=false.

Argument Does
gps:=false no GPS anywhere: no driver, and localization without it
gps_driver:=ublox which GPS driver: ublox (the default, Tentative: Q18), nmea, or ublox_dgnss (apt only, the car)
map:=, start_x:=, start_y:=, start_yaw:= Nav2's map, and where the car starts on it
lidar:=false no lidar anywhere, whatever the machine file says
actuators:=uart who drives the actuators: uart (the default: the Motor Pi's legacy_uart_bridge) or can (the CAN spine)

Try Jazzy on the car before the reflash

Pixi also runs on the car's ARM computers, on the Ubuntu 22.04 they have now. So the team can try this stack on the car first, and reflash later. It resolves, but is untested on the car.

No internet on the car? Use the USB kit

pixi run car-kit on a Mac makes a 1.8 GB folder that installs all of this offline, without sudo, into ~/aav-jazzy: From a USB stick.

  1. Stop the 2025-26 software: it is Humble, and Humble and Jazzy don't mix.
  2. On the Orin and the Motor Pi, install Pixi and copy the code, as on Your Mac (steps 2 to 4). It needs a 64-bit OS: uname -m must say aarch64.
  3. Run pixi run car orin on the Orin, and pixi run car motor_pi on the Motor Pi.

Moving the Orin to JetPack 7.2

It's a reflash, not an upgrade:

  1. Back up /home/aavjetson and every workspace first. It holds the only copy of the 2025-26 YOLO detector and camera/LiDAR setup. Better still, take a full image with l4t_backup_restore.sh.
  2. Check cat /etc/nv_tegra_release and the module's part number. Module 699-13701-0005-502 has a reported flashing problem; -501 works.
  3. Flash with SDK Manager from an Ubuntu 22.04 or 24.04 x86 PC, or use the dev kit's USB installer.
  4. Install Jazzy as above. Move the Pis to Ubuntu 24.04 at the same time.
