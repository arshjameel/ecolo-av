Every backend takes the same ego command (through the output mux), so the drivers, mux, ego and localization run unchanged whether the "car" is a turtle, Gazebo, or the real thing. Climb the ladder one rung at a time.

pixi run sim and pixi run turtle stay on this computer: other terminals here see them, other computers don't. So a simulated car never meets the real one. To share one on purpose: AAV_DISCOVERY=SUBNET pixi run sim.

The test ladder

Rung Runs Proves
1. Unit tests: tools/test.sh (pixi run test adds the ROS tests) the maths and protocols, without ROS ego's maths, the CAN frames, the spine logic
2. turtlesim: pixi run turtle mux, ego, scripted driver, ekf_local the command path, end to end
3. Gazebo: pixi run sim the whole stack, on a simulated car with an IMU and GPS; in the road world, its camera and radar too localization and Nav2; in the road world, the car's whole graph: pixi run sim-check
4. Replay localization (and Nav2) on a recorded drive config changes, against real sensor data
4b. The bench: pixi run bench the car's own graph: the spine bridge and CAN frames, the spine's firmware logic on a model car, pretend sensors the car's software path, end to end, before the car: Bench mode
5. Car on stands the real backend, wheels off the ground the firmware link, signs and limits
6. Car everything, with a safety driver the phase you're on

More drivers in the turtle run

Joystick: plug it in, start with pixi run turtle teleop:=true, hold the deadman (the trigger) and steer.

Scripted drive: speed up, hold, slow down, on a gentle left curve:

ros2 action send_goal /scripted_drive aav_interfaces/action/ScriptedDrive \
  "{target_speed: 1.0, acceleration: 0.5, deceleration: 1.0, hold_time: 3.0, curvature: 0.2}" --feedback

The keyboard or joystick overrides the script at once. Let go, and the script carries on.

E-stop: ros2 topic pub --once /safety/estop std_msgs/msg/Bool "{data: true}" blocks every driver. Publish false to clear it.

The actuator model

Added 15 Oct (full-simulation.md, step 3). Gazebo used to set the speed itself (+1.5 / -3.0 m/s²) and steer at once. Now gazebo_adapter puts a model of the actuators in between, 50 times a second, on Gazebo's clock:

ego's speed ──> speed loop (the spine's, in Python) ──> throttle %, brake %
                                                          │
ego's angle ───────────────────────────────────────┐      ▼
                                       ACTUATOR MODEL (actuator_model.py)
                                       throttle → push, brake → stop, drag
                                       steering: deadband → motor speed → lag → offset
                                                          │
                                                          ▼
                                       Gazebo: this speed, this angle
Part Its numbers (vehicle.yaml, actuators:) Measured by
Throttle max_accel 1.5 m/s², throttle_deadband 0, throttle_lag 0.1 s tests 4.1, 4.4
Coasting drag 0.1 /s test 4.2
Brake max_brake 3.0 m/s², brake_lag 0.2 s test 4.3
Steering steer_rate 0.8 rad/s, steer_lag 0.1 s, steer_offset 0, steer_deadband 0.005 rad tests 3.10-3.12, 4.5

Every number is a guess

Chosen to match Gazebo's old limits and the bench's spine_sim. Swap in the measured ones once the tests are done: no code changes.

  • Gazebo's own limits (aav.gazebo.xacro) are now ±10 m/s², so the model limits, not Gazebo.
  • Gazebo's steering_limit is not max_steering_angle. Gazebo turns it into a smallest circle, wheelbase ÷ sin(limit), so 0.5 stopped the car at 0.447 rad. The launch file passes vehicle.gazebo_steering_limit (0.578) instead: the middle wheel then reaches 0.5. Measured: 0.484 rad at full lock, the last 3% tyre slip (Actuator tests).
  • actuator_model:=false keeps the old behaviour (in the adapter), to compare the two.
  • No command for 0.2 s: the model brakes to a stop, like the spine's watchdog. For the spine's real watchdog, e-stops and arming: spine:=true.
  • Plot command against measured: /vehicle/steering, /vehicle/throttle, /vehicle/brake (Foxglove or PlotJuggler).
  • Check it: pixi run actuator-test <test> --sim runs the car's stage 3-4 tests in Gazebo and prints these numbers back (Actuator tests). On 15 Oct all but the throttle deadband came back within a few percent.
  • The IMU feels the model (15 Oct): Gazebo's own IMU never felt the car speed up, brake or turn (it reads only gravity, noise and contact bumps). gazebo_imu puts the car's forward and sideways acceleration at imu_link in its place (worked out from Gazebo's odometry, which follows the model), with the configured noise (aav_gazebo/imu.py). The EKFs use only the yaw rate, so nothing else changes.

How the simulated car connects:

  • Gazebo plays the car, with Ackermann steering, an IMU and a GPS.

  • Nodes of ours turn those into the real drivers' topics, one per part, as on the car:

    Node Gives On the car, instead
    gazebo_adapter the car: /vehicle/odom, the wheels, the actuators, the status spine_bridge
    gazebo_imu /sensors/imu/data_raw imu_node (Rust)
    gazebo_gps /sensors/gps/fix ublox_gps
    gazebo_radar /sensors/radar/points (road world) the TI driver
    gazebo_camera the front left picture, only with faults:=true usb_cam

    Each is a process of its own, so each runs on its own core: until 22 Oct one Python node did all of it on one thread, and the IMU sometimes went quiet behind it. - The IMU filter, both EKFs and navsat_transform run with the car's own configs, on simulated time. - Map (0, 0) is where the car starts, facing east. - In the road world, the car also has its front camera and a radar stand-in.

To drive it:

  • Keyboard: pixi run keyboard --sim.
  • A Nav2 goal: in RViz, click 2D Goal Pose, then click and drag on the map. Any human input overrides Nav2.

No GPU, or in a virtual machine?

Start it with gui:=false, and watch in RViz or Foxglove instead. The empty and test_lot worlds render nothing, so they run anywhere. The road world renders the cameras and the lidar: on Linux with no GPU, start it through tools/software_gl.sh, as tools/software_gl.sh pixi run sim gui:=false (Mesa's software OpenGL). Without it, Gazebo crashes as the world loads (Unable to load Ogre Plugin), and the car never appears. works on oirp-spss, 23 Oct.

The car never appears?

If the log keeps saying Requesting list of world names, Gazebo's programs can't find each other: they use multicast, and some networks and firewalls block it. Run export GZ_IP=127.0.0.1 in every terminal, then start again. On a shared computer, also set your own GZ_PARTITION=<any name>, so your simulator doesn't meet someone else's.

The lidar: Gazebo only

The car has a Velodyne VLP-16 on its roof, read by the stock velodyne driver (on by default on the car; untested with the real lidar). Gazebo has a generic 16-beam one in its place. It's on by default (15 Oct) in the road and test_lot worlds: pixi run sim world:=road or world:=test_lot.
Where lidar_link, in vehicle.yaml: on the roof tripod, 0.9 m ahead of the rear axle, 1.8 m up (Ben's placement, 15 Oct, until it's measured)
Why a mast at 0.1 m above the roof, the beam 11 degrees down hit the car's own roof: 904 points a sweep at 0.5 m. At 0.4 m nothing hits the car
Size 1800 x 16 points, 0.9 MB a cloud, so it's bridged reliably: best effort loses big messages (see Mac)
Who reads it Nav2, since 15 Oct (below): lidar_scan flattens it into a 2D scan for the local costmap and collision_monitor
Turn it off lidar:=false: the simulated sensor leaves the URDF (the frame stays), and its bridge doesn't start
On the Mac, alone stable: 10.0 Hz, real-time factor 0.99, Gazebo at about 80% of one core with the camera and radar too. sim-check passes with it
On the Mac, with YOLO too, the morning of 15 Oct flaky: sim-check --perception failed 3 runs out of 3 with the lidar on (a stuck global EKF twice, a 2.5 s stall once). Without it, it passed (see sim-check)
Why it was off anything that shows the lidar (RViz, a check) pulls 9 MB/s of reliable clouds. Fast DDS's shared memory fails on the Mac (open_and_lock_file failed), so they go over loopback UDP, and with YOLO running, other processes start missing messages (one lost /clock for 2 minutes)
Now on by default again: with the Mac quiet, everything together passed twice (below). If a run stalls, check for leftover simulators first (ps aux \| grep gz), then try lidar:=false

The lidar in Nav2 (15 Oct)

 /sensors/lidar/points ─► lidar_scan ─► /sensors/lidar/scan ─┬─► local costmap: lidar_layer
  (0.9 MB, 10 Hz,          (aav_lidar)   (720 ranges, 3 kB)   └─► collision_monitor: stop zone
   reliable)
What counts points from 0.3 m above the road to 0.5 m over the roof (2.0 m): vehicle.obstacle_heights, from vehicle.yaml. The road, kerbs and overhead branches don't; nor do points on the car itself
The scan 720 directions (0.5°), each the nearest point, flat from base_link; inf where nothing is, which clears the costmap
Its own costmap layer lidar_layer, so its clearing never wipes the radar's marks
Switch navigation.launch.py lidar:=true. sim.launch.py passes it where the world renders the lidar. The car: on by default (the velodyne driver; car.launch.py lidar:=false turns it off)
CPU lidar_scan about 4% of one core; Nav2's two readers get 3 kB a scan instead of 0.9 MB
Why not the stock pointcloud_to_laserscan tried first: it subscribes best effort, and on a Mac no 0.9 MB cloud ever arrives that way (Mac). Ours subscribes reliably
Its blind spot from 1.8 m up, the lowest beam (15° down) meets a 1 m box only 2.1 m ahead of the bumper, and the road only 4.9 m ahead. In the stop zone (bumper to 1 m ahead) it sees only what stands over about 1.3 m: a person, a car, a post. Low things close in front are the radar's
Proof pixi run sim-check --lidar-obstacle: the radar off, a person-sized post (0.5 x 0.5 x 1.8 m) 15 m ahead. The car stood still 0.16-0.55 m before it (two runs), the stop zone fired from the lidar, the costmap marked it (100 of 100); with the post gone, it drove on to its goal

The rings are where each beam meets the flat ground. The far rings come out slightly polygonal: Gazebo's gpu_lidar renders depth in a few camera views, and at grazing angles small depth errors become large range errors.

Sensor failures on purpose

full-simulation.md step 6 (15 Oct): make a simulated sensor fail, and check the car stops, safely and loudly.

Make one fail

pixi run sim world:=road faults:=true     # faults:=true only for the camera
pixi run sim-fault gps stop               # the GPS goes quiet
pixi run sim-fault gps ok                 # mended
pixi run sim-fault clear                  # after a GPS jump or a lost HUD: a person says all is right
Sensor Topic it breaks Faults
gps /sensors/gps/fix stop, freeze, nan, jump (20 m north)
imu /sensors/imu/data_raw stop, freeze, nan
odom the wheels: /vehicle/odom, /vehicle/wheels stop, freeze, nan
radar /sensors/radar/points stop, freeze
camera /sensors/camera/front_left/image_raw (with faults:=true) stop, freeze

freeze sends the last good message again, with fresh stamps: it looks alive. It's a parameter, fault.<sensor>, of that sensor's node (gazebo_gps, gazebo_imu, gazebo_radar, gazebo_camera; the wheels' is gazebo_adapter's). The logic is aav_gazebo/faults.py.

The sensor watchdog

aav_safety's sensor_watchdog watches what Nav2 and the AI slot need. While one isn't right, its twist_mux lock (priority 30, as the stop sign) holds them; people and tests still drive. It says why on /safety/sensor_watchdog/state, on the HUD (a red banner over the camera), on the map window (a banner across the map), in the log and on /diagnostics.

Input Topic Wrong when Then
odom /vehicle/odom quiet 0.5 s; NaN; the wheels disagree with the IMU or the GPS for 1 s (below), latched until cleared stop
imu /sensors/imu/data quiet 0.5 s; NaN; the same for 1 s stop
gps /sensors/gps/fix no good fix for 2 s (NaN or no fix count as none); a jump between two fixes of more than 15 m/s x the time between their stamps + 5 m (for noise), latched until cleared stop
local, global the EKFs' /localization/odom/* quiet 0.5 s; NaN stop
camera the front left picture quiet 1 s; the same picture for 1 s while the wheels turn stop (only where something reads it: perception, lane, camera obstacles)
radar /sensors/radar/points quiet 1 s warn: collision_monitor already stops Nav2
front_left_stream, front_right_stream a front camera's stream, through its detections on /perception/detections (its frame_id only: camera pipeline) quiet 1 s; NaN in a box stop (the car, where car.launch.py starts the streams)
hud /hud/heartbeat (the HUD's screen is alive) quiet 1 s; the count stuck for 1 s; after its first 5 s, latched as hud LOST until cleared (24 Oct) stop (only where a HUD is expected: the car, hud:=true, watch_hud:=true)

It runs in Gazebo (watchdog:=true), on the bench (always), and on the car next to the mux (odom, IMU, GPS, the EKFs, the HUD, and the camera streams it starts). The checks are aav_safety/watchdog.py and wheel_check.py, with no ROS, and their tests.

If the watchdog itself dies

The lock is fail-safe (15 Oct). The watchdog sends false 10 times a second: a heartbeat. twist_mux locks a lock with a timeout when it goes quiet (checked in its source: LockTopicHandle::isLocked), so 1 s of silence holds Nav2 too.

 sensor_watchdog --false, 10 Hz--> twist_mux sensors lock (priority 30, timeout 1 s)
       dies, hangs, never starts  -->  silence > 1 s  -->  locked: Nav2 and AI held
                                                           joystick, keyboard, tests: still drive
Profile Watchdog Lock

Frozen wheels

A wheel-speed driver stuck in a loop sends the same speed with fresh stamps. At a steady speed that looks like a car at a steady speed. wheel_check.py cross-checks the wheels:

Against How Catches
The IMU's acceleration over 1.5 s: the wheels' change in speed vs the forward acceleration, added up a frozen speed while the car speeds up or brakes
The IMU's gyro over 1.5 s: the mean turn rates a frozen turn rate while the car steers
The GPS over 10 s: the speed of a line fitted to the fixes vs one fitted to where the wheels say the car went a speed that stays wrong

Any gap over its limit (0.3 m/s, 0.15 rad/s, 0.15 m/s) for 1 s is DISAGREE, latched until pixi run sim-fault clear. Wheels frozen at a speed the car really keeps are still right, so nothing is said until the car's speed or turn changes. A frozen IMU or GPS is left out (its own input says FROZEN), not blamed on the wheels.

Normal driving, Gazebo (sim-check's wheels vs IMU and GPS, the obstacle's braking too): worst speed gap 0.09-0.15 m/s and turn 0.006-0.010 rad/s (8 runs): half the limits or less. The GPS: 0.12-0.14 m/s over the old 6 s window (5 runs), 0.04-0.08 m/s over 10 s (4 runs, below): half the limit or less. The limits are Gazebo's: on the car, read worst_*_gap on /diagnostics after a normal drive, and set them well above.

Frozen wheels and MPPI

Found 24 Oct, when odom freeze failed in most --faults runs. Since 22 Oct MPPI is Nav2's default, and MPPI plans from the speed the wheels say. So frozen wheels hold the car near the frozen speed: it drives on only 0.1-0.2 m/s faster.

                          wheels frozen at 0.2 m/s, Nav2 asks about 0.4    -> 0.2 m/s wrong

10 s and 0.15 m/s: twice the worst noise or more (three sim-check --faults runs saw 0.04-0.08 m/s), and a big error is caught as fast as before. Still not caught: wheels wrong by under 0.15 m/s (frozen at 0.5 under MPPI). sim-check --faults now freezes them at 0.2 m/s, while the car still speeds up, and counts them wrong only once they're off by more than these limits.

The global EKF and a GPS jump

ekf_global now refuses a GPS fix more than 10 sigma from where it thinks the car is (odom1_pose_rejection_threshold, Mahalanobis distance). The first fix on the car could be far from start_x, start_y (or the datum): so x and y start 100 m unsure, and the first fix always gets in. tools/tests/test_ekf_config.py checks the numbers.

20 m jump (gps jump) The global EKF, 10 s on
Before (no gate), no watchdog 19.3 m from the truth
Gate, with the watchdog (the car stops) 0.1-0.5 m (three runs)
Gate, no watchdog (the car drives on) 19.4 m: driving, the filter grows unsure of its heading, and after a few seconds it takes the jump. Then it refuses the good fixes for a while (8.5 m out at the next fault)

So the gate keeps the map position right while the watchdog holds the car; the watchdog's latched JUMP stays the guard, and a person checks the position before clearing it.

Replay a recorded drive

On the car, record a drive: tools/record.sh parking_lot_test writes bags/<date>_parking_lot_test/. Then re-run localization against it on any laptop:

ros2 launch aav_bringup replay.launch.py
ros2 bag play bags/<the bag> --clock --topics /vehicle/odom /sensors/imu/data_raw /sensors/gps/fix /tf_static

A bag from Gazebo carries simulated time. Play its own /clock instead of --clock: ros2 bag play bags/<the bag> --topics /clock /vehicle/odom /sensors/imu/data_raw /sensors/gps/fix /tf_static. pixi run tools/ros.sh python3 tools/check_graph.py --profile replay checks the result.

Change an EKF setting, replay, compare the path. That's how to tune localization without the car.

tools/replay_commands.sh bags/<the bag> plays the recorded commands back into the mux as replay (priority 40). It's open loop, so the car drifts from the original path.

When nothing moves

Work down the chain:

# Ask Check
1 Is a driver publishing? ros2 topic hz /drivers/keyboard/cmd_vel (or joy, scripted, nav)
2 Did the mux pick it? ros2 topic echo /control/cmd_vel. If it's silent, look for a latched e-stop: ros2 topic echo /safety/estop
3 Is ego converting it? ros2 topic echo /ego/actuator_cmd: it's always 50 Hz, so look at the speed
4 Is the output mux open, and a backend listening? ros2 topic echo /safety/output_mux/state says OPEN; ros2 topic info /control/gazebo/actuator_cmd -v
5 In Gazebo or replay: is everything on sim time? a node on wall-clock time ignores sim-time messages
6 Does the graph match the contract? pixi run check sim (or road, replay)
7 Is the sensor watchdog holding Nav2? ros2 topic echo /safety/sensor_watchdog/state: anything but OK says which sensor and why
