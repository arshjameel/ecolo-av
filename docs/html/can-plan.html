Ben's KEFC request (October 2026, tab "Bens Mods") puts steering, braking and throttle on a CAN bus. Our code had a CAN contract, firmware/can/aav.dbc (v0.1.0). This page compares the two. Since 15 Oct, aav.dbc v0.2.0 follows the plan.

Status: built in software, hardware not decided. DBC v0.2.0, spine_bridge and the bench use it (merged 15 Oct, so the software is ready). Whether the car gets CAN and the wheel node boards is the hardware lead's decision, with the team (Ben, 15 Oct: "I am waiting on the other people to make the final decisions. There is a hardware lead that isn't me"). No parts are ordered until then.

What runs where, today

Machine Runs Topics
Orin socket_can_receiver (no sender) and spine_bridge role:=sensors /can/rx in; /vehicle/odom, /vehicle/wheels out
Motor Pi legacy_uart_bridge /control/car/actuator_cmd in (from the output mux); UART frames out

spine_bridge role:=sensors can't drive: it has no /can/tx publisher, no /spine/arm service and no /safety/estop subscription, and it ignores the spine's frames (0x180, 0x181). On /system/source it names only odometry and wheels, never an actuator. The output mux's guard test checks this, in Rust and in Python.

/vehicle/odom, role sensors How
Speed the two front wheels' mean, while both are fresh. One stale: nothing (the sensor watchdog sees it stop)
Sign the wheel's, if it measures it; else the last command's (one Hall sensor can't tell direction)
Yaw rate not measured (covariance 1e3): the steering angle isn't on this bus. ekf_local takes it from the IMU

Give every machine the same actuators:=

actuators:=can on the Orin and uart on the Motor Pi would start two backends. The wiring makes it moot (the ESP32 listens on one link), but don't mix them.

The 2025-26 UDP wheel encoder (encoder_udp, a Pico 2) is off in motor_pi.yaml: the wheels are on CAN now, and two /vehicle/odom publishers would stop the output mux.

The Rust ESP32 firmware's 100 ms command timeout then sits on the UART link, not on CAN: see First flash on the bench. Open questions for the hardware lead: Questions.

What is different

# Difference KEFC PDF Our DBC Proposed
1 Which board is "the spine" the existing ESP32 control board a new Pico 2 the ESP32 control board. It is already on the car, with its CAN plug
2 What 0x100 carries steering, brake and throttle targets target speed and steering angle ours. The PDF's own loop table has the board running the speed loop, so it needs a speed, not a throttle
3 0x010 a heartbeat the software e-stop ours. Every frame's counter is already the heartbeat
4 Wheel speed 0x200 left, 0x201 right, 100 Hz one wheel_ticks in 0x180 add 0x200 and 0x201 from the PDF
5 Timeout 100 ms 200 ms 100 ms, from the PDF
6 Steering position from the KTC-100 pot, via the Jrk measured_steering_angle in 0x180 the same: the board reads it from the Jrk

Rust on an ESP32

The ESP32 and ESP32-S3 use Xtensa cores. Rust needs Espressif's toolchain (espup), not the stock one in Pixi. It is well supported: esp-hal has Embassy and a CAN (TWAI) driver.
