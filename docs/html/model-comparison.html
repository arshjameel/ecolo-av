plan.md item S6, 16 Oct 2026. Two questions:

  1. Seeing: is YOLO26 or RF-DETR better than our YOLO11 at people and stop signs?
  2. Plain English: is a newer local language model better than Qwen3 at turning "drive 10 m forward" into the drive server's tool calls?

The short version - Now: RF-DETR Nano is the car's detector (Ben, 23 Oct: "I thought we were skipping yolo and using the other one"), the detector node's default, in TensorRT on the Orin. YOLO stays as detector:=yolo (Perception). - Why RF-DETR Nano won (16 Oct). It saw Gazebo's stop sign from 20 m (YOLO11n: 10 m) and found people in 4 of 5 photos (YOLO11n: 3), with no false finds. It's Apache-2.0, so the AGPL question goes away. On a Mac it is as fast as YOLO11n (16-17 ms vs 12-21 ms). Its cost: 12 times the weights (30 M), and 2.5 times slower on a CPU alone. Not tried on the Orin yet. - YOLO26 brings nothing here. YOLO26n scored the same as YOLO11n, picture for picture, and has the same AGPL-3.0 licence. - Language: Gemma 4 E4B planned all 23 requests right (Qwen3-4B, our default: 21), at 0.5 s a step, in 5 GB, Apache-2.0. Ministral 3 3B (22, in 2.8 GB) is the small runner-up. The default stays Qwen3-4B until the team agrees: 23 requests is a small test. - New: an OpenAI-compatible backend (aav_language/llm_openai.py), so the same agent can use llama.cpp or TensorRT-LLM on the Orin. Tried through mlx_lm.server: 22 of 23.

Licences: what AGPL-3.0 means for us

Ultralytics (YOLO11, YOLO26) RF-DETR Nano, Small (Roboflow)
Code AGPL-3.0 Apache-2.0
The trained weights AGPL-3.0, Ultralytics says, our own fine-tuned ones too Apache-2.0
Our code that uses it must be shared under AGPL-3.0 terms whenever we give the program to anyone, or let people use it over a network any licence
A closed or paid version later needs an Ultralytics Enterprise licence allowed: keep the notices
  • Our repo is public, so sharing the source is easy. But it has no licence file yet: by default that means "all rights reserved", which doesn't fit with AGPL code in the same program. With YOLO, the team should put the repo, or at least aav_detector, under AGPL-3.0 (a team decision; not legal advice).
  • The network clause: if the HUD's web page ever shows YOLO's boxes to people over the network, that counts as use over a network.
  • The 2024-25 best.pt was trained with Ultralytics: Ultralytics counts it as AGPL too.
  • RF-DETR's larger models (XLarge, 2XLarge, in rfdetr_plus) have a different, Roboflow licence. Nano, Small, Medium, Base and Large are Apache-2.0.

Typing just "stop" or "estop" never reaches a model (react.FAST), so a model's miss there matters less; the agent's Ctrl-C sends stop() too.

Two models needed the agent to learn their format

Gemma 4 and Ministral 3 first scored 0: they answered in their own tool-call formats, which the agent couldn't read. react.parse_reply now reads both:

Gemma 4      <|tool_call>call:turn{angle_deg:45,direction:<|"|>right<|"|>}<tool_call|>
Ministral 3  [TOOL_CALLS]turn[ARGS]{"angle_deg": 45, "direction": "right"}

The recommendation

  • Gemma 4 E4B is the best candidate for the default: all 23, quick, Apache-2.0. Its official licence is Apache-2.0 (google/gemma-4-e4b-it); the MLX copy's page still says "gemma": go by Google's. Its download is 5.2 GB.
  • Before switching: add 20 or so requests to eval_set.py (one or two answers either way is noise at 23), and try it on the Orin.
  • On the Orin (AGX): the 3-8 B models fit easily. The two 15-20 GB mixture-of-experts models fit a 64 GB Orin too, and are quick for their size (only 3-4 B weights work per word), but scored no better.

The same agent on the Orin: the OpenAI-compatible backend

MLX runs only on Apple silicon. The Orin needs llama.cpp (CUDA) or TensorRT-LLM. All of them, and Ollama, serve the same OpenAI /v1/chat/completions API, so one small client covers every one: aav_language/llm_openai.py (standard library only).

3. Two open-source agents: what we could borrow

Ben mentioned two agent harnesses. Both are MIT-licensed TypeScript; we read them as references only, and copied no code.

pi (Mario Zechner) opencode
Repo badlogic/pi-mono, now earendil-works/pi sst/opencode, now anomalyco/opencode
The loop call the model, run its tool calls, add the results, repeat until no tool calls the same, one step at a time, with a step limit per agent
Tool calls in one reply run together, unless a tool says "one at a time" run together
Bad arguments checked against the tool's JSON schema; the error, field by field, goes back to the model the same, "update the arguments and call the tool again"
Asking a person none by design (run it in a container) per tool: allow, ask or deny; the last matching rule wins
Stopping an abort signal reaches every tool; messages typed meanwhile are queued ("steer") interrupt cancels running tools; a queue for typed messages
Too many steps no limit tools switched off; the model must sum up what it did and what's left
Local models any OpenAI-compatible server (Ollama, llama.cpp --jinja) the same; raise Ollama's context to 16-32 k for tool calls
Where packages/agent/src/agent-loop.ts packages/core/src/session/runner/llm.ts, permission.ts

What our node (react.py) could borrow:

Idea From For us
Check arguments against the tool's schema, send the errors back once both fewer "unreadable" steps from small models
Allow / ask / deny per tool opencode what we do by hand: status, stop, estop allowed; moves asked (the "yes")
At the step limit, switch tools off and make the model sum up opencode a clear answer instead of "I stopped planning"
Never run a reply cut off by the token limit pi a half-written move must not run
Typed text during a drive is queued, not lost; one abort reaches everything pi "stop" while driving already works; "then turn left" could queue
One OpenAI-compatible client both done: llm_openai.py
