For whoever puts the whole thing together. How it fits explains the car's software: sensors, drivers, the mux, ego, backends. This page explains everything around it: the repo, the environment, the contracts, the profiles, the computers, the tests, and how a change goes from an idea to the car.

The three contracts

Three files say how the parts must talk. Change the contract first, then the code, and the checks tell you if the two disagree.

Contract Holds Checked by After you change it
docs/interfaces.yaml every topic: its type, who publishes it, who reads it, and in which profiles it must be live pixi run check <profile> on a running system; pixi run test checks that the Topics page matches pixi run python tools/gen_interfaces_md.py > docs/interfaces.md
firmware/can/aav.dbc every CAN frame between ROS and the spine test vectors, shared by the Python codec and the Rust tests update can_codec.py and protocol.rs, run firmware/can/gen_test_vectors.py, run both test suites
ros/bringup/aav_description/config/vehicle.yaml every measurement of the car its unit test; ego, the URDF, Nav2 and the adapters all read it measure the car: Car numbers

The environment: Pixi

Pixi installs ROS 2 Jazzy and every tool into the repo's own .pixi folder, from RoboStack and conda-forge. No admin rights, and the same versions on every computer, because pixi.lock pins them all.

Platform in pixi.toml Who uses it
linux-64 Linux laptops and oirp-spss
linux-aarch64 the car's ARM computers (Orin, Pis), to run Jazzy before a reflash
osx-arm64, osx-64 Macs, Apple Silicon and Intel (macOS 14 or newer)
Command Does
pixi install downloads and installs everything in pixi.lock (about 7 GB the first time)
pixi run <task> runs a task inside the environment: see the next table
pixi run <any command> runs any command inside it, e.g. pixi run tools/ros.sh ros2 topic list
pixi shell a terminal inside it; then source install/setup.zsh (Mac) or setup.bash (Linux)
pixi run -e ml <task> the same, in the ml environment: PyTorch, RF-DETR and YOLO on top of everything else
Environment Holds Who uses it
default ROS 2 Jazzy, Gazebo, Nav2, Rust, the compilers everyone
ml the default, plus PyTorch, RF-DETR, Ultralytics (YOLO) and, on Macs, Core ML tools whoever runs the detector: pixi run detect, pixi run -e ml bench perception:=true. Linux PCs and Macs only
docs Markdown and WeasyPrint pixi run docs
mcp the default, plus the MCP Python SDK an AI app, through .mcp.json: AI apps (MCP)
firmware Python and PlatformIO, no ROS today's C++ boards: pixi run -e firmware legacy-esp32
llm mcp, plus MLX (Macs with Apple silicon) plain-English driving: pixi run -e llm talk (Plain English)
routes Valhalla, no ROS the street router: pixi run -e routes router (Routes)
gst GStreamer, no ROS the camera stream's fast decoder (camera pipeline)
calib ROS's camera_calibration pixi run calibrate-camera (camera calibration)

Macs only: GNU coreutils

On a Mac, macOS's System Integrity Protection deletes DYLD_LIBRARY_PATH whenever /bin/sh or /usr/bin/env starts, and ROS needs that setting to load our own messages. So the Mac environment adds GNU coreutils for colcon test, and scripts that run ROS commands go through tools/ros.sh. Details: Your Mac.

How a change goes from an idea to the car

# Step Where
1 Change the contract first, if the change touches one the contracts table above
2 Write the logic in a plain module, with tests ros/<area>/<package>/
3 Keep the node thin, with a docstring of what it reads and writes the same package
4 Register it: a launch profile, the mux (drivers), tools/test.sh (tests) Build a driver
5 pixi run test, then the turtle, then pixi run check sim in Gazebo Simulation
6 Update the docs page, then pixi run docs docs/
7 Commit small, each commit passing the tests; inherited code gets a PROVENANCE.md line git
8 On the car: stands first, then the ground at walking pace, with a safety driver the test ladder

Sharing the code

The repo is on GitHub: git@github.com:AAV-2025-2026/ecolo-av.git, public: anyone can read it. Changes reach main only through a pull request from your own fork and the merge queue: Contributing has the steps.

Task Command
Get it, take newer work, share yours fork, clone, branch, pull request: Contributing
Hand it to a laptop with no GitHub access git bundle create ../aav.bundle HEAD main (keep HEAD, or a clone checks out nothing), then git clone aav.bundle aav there

CI (.github/workflows/test.yml) runs pixi run test on Linux for every push to main, every pull request and every merge-queue entry, and on a Mac every night. The results are on the repo's Actions tab.

In your fork too. Turn Actions on once in your fork (its Actions tab, then "I understand my workflows, go ahead and enable them"). From then on every push to a branch there runs linux, arm and car-kit, so you see green or red before you open the pull request. The nightly mac and sim runs stay in the team's repo.

Job Computer When What

arm Ubuntu 24.04, 64-bit ARM, like the Orin and the Pis the same 12 min: pixi run test; the HUD and the map window built as ARM programs, and each drawn once on a virtual screen (picture: the artifact arm-screens)
mac macOS 15, Apple Silicon every night (team's repo) pixi run test, the MCP server

Every job also runs from the Actions tab (Run workflow).

Every night it also runs sim-check --obstacle (Gazebo, headless) on Linux: the job sim. New on 22 Oct and still on trial: GitHub's computers have no GPU, so the cameras render in software (Mesa's llvmpipe, through tools/software_gl.sh), and a failure there doesn't fail the night yet (continue-on-error).

Reading a CI failure without signing in

A job's log needs a GitHub sign-in. Its annotations don't: when the test step fails, tools/ci_annotate.py prints one annotation per failing test, with its error message.

Step Open this (curl -s works too)
1. Find the job https://api.github.com/repos/AAV-2025-2026/ecolo-av/commits/<sha>/check-runs: note the linux job's id
2. Read its failures https://api.github.com/repos/AAV-2025-2026/ecolo-av/check-runs/<id>/annotations

Without a sign-in GitHub allows 60 of these calls an hour, so don't poll fast. A step keeps at most 10 annotations: 9 failing tests, then the rest by name, or the log's last 40 lines.

The sim job's annotations (ci_annotate.py --sim): each FAIL line of sim-check, then the launch log's last errors (Gazebo's crash, a node that died). Its whole logs (sim-check's output, the launch log, every node's ROS log) are kept 14 days as the artifact sim-logs. Anyone can list artifacts (https://api.github.com/repos/AAV-2025-2026/ecolo-av/actions/artifacts), but downloading one needs a sign-in: on the run's page, or gh run download <run id> -n sim-logs.

PowerShell on the Linux runner

GitHub's Ubuntu runners set PSModulePath, which makes colcon set each package's environment through PowerShell; our own packages then go missing from later builds. The workflow empties PSModulePath, so colcon uses sh, as on a laptop.

What never goes in git

Build output (build/, install/, log/, .pixi/, target/), recordings (bags/), and secrets. .gitignore lists them. Downloaded third-party source, such as ROS's own code, lives in vendor/, which git doesn't track: pixi run vendor.
