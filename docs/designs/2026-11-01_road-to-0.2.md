## Overview

On 1 November we talked through a lot in one night. This page keeps it all in one place,
so nothing is lost, and so reviewers can ask: **are we doing too much, and in the right
order?**

The aim: **0.2 = sim-complete, car-ready.** Everything merged and tested in Gazebo, the
docs and the runbooks done. **0.3 = it drove**, after car day.

How solid we are today: every test passes (1513, 0 failures) and every profile runs in
Gazebo. **Nothing in this stack has moved the real car yet.**

## The direction for the algorithms

Today the stack has layers: localization, perception, planning, control. Each layer has a
default and some trials beside it. Ben, 1 Nov: "we still need the layers as we are
learning. Eventually we can collapse it down."

1. Keep the layers and their defaults. Score the trials against them.
2. Add learned parts one at a time **inside** a layer (the diffusion planner as a Nav2
   planner), with the classic stack as the safety guard (the "simplex" idea).
3. Only later, with enough of our own driving data, try a model that does more than one
   layer.

## The review (1 Nov, night)

Three Elephant-Goldfish reviewers read this page against the repo: scope (zoom-out),
design, and "could a student run car day alone?" (readiness).

**Their verdict, in one line:** too wide for a car that hasn't moved. Make 0.2 small, and
split car day into a day that destroys nothing and a day that upgrades.

### What all three said

| # | Finding | Fix |
|---|---|---|
| 1 | The list mixes done work, decisions and ideas | three lists: done in 0.2, decided, left for 0.2 (5 rows at most) |
| 2 | "Car-ready" has no test you can pass | a checklist: `pixi run test`, `car-day-check` 0 missing, `esp qemu-check`, `car_setup.sh` dry run for every role, the TODO 74 gaps closed or signed |
| 3 | The first joystick moves have open gaps (TODO 74) | build a joystick-alive check now; a **throttle cap** in the firmware (not "speed cap": the ESP32 can't see speed); Rust firmware only; the Kar-Tech stop held by a second person |
| 4 | Upgrading the Pis destroys the way back (Humble, the C++ bridge, the IMU and GPS on the localization Pi) | Day A changes nothing; upgrades on Day B or in 0.3; a full card image of every Pi, checked, on the encrypted drive |
| 5 | Two runbooks (car-day.md, car-setup.md) disagree on order and on the ground | car-day.md owns the day; car-setup.md only sets up one computer |
| 6 | More screens than three; the cockpit and the debug HUD overlap | freeze screens for 0.2; in 0.3 merge cockpit and debug HUD; the hardware panel stays apart (it drives) |
| 7 | Ideas in a release that can't test them | to 0.3 or later: Initial D HUD, diffusion, talking model, Calm, algorithm switch, Python speed, brake and throttle setting |

### The order the reviewers agree on

1. Back up everything (full images, checked). Nothing upgraded.
2. Steering ends, Way A, on stands.
3. Brake check on stands.
4. Rust ESP32 on stands; joystick on stands, the joystick-off test included.
5. Ground, walking pace: a named person signs.
6. The car tests, bagged with the lidar; the map.
7. Autonomy.

Upgrades and the Orin reflash: a second day, after the restores are proven.
