# The debug HUD: what the car sees, and what it thinks

* **Author:** Ben (the ask), written up 29 Oct 2026
* **Status:** Tentative: revised after the EGM review (design, zoom-out), 29 Oct

## The idea in one line

A second raylib program, `debug_hud`, beside the in-car `hud`: a 3D view of the lidar's
**cubes** around the car, where each localizer **thinks** the car is, and a panel of every
sensor and actuator **straight from its own node**. `pixi run debugdemo` is `pixi run demo`
plus `debug_hud`.

## Version 1: one thin slice, end to end

```
┌──────────────────────── 3D view (orbit with the mouse) ─────────────────┬─ panel ──────┐
│  this scan's cubes, 20 cm, coloured by height (ground darker)            │ IMU   OK 0.0s│
│  the car's outline (vehicle.yaml)                                        │ GPS   OK 0.4s│
│  EKF local (blue)  EKF global (green)  truth (white, sim)  AMCL (orange) │ lidar OK 0.1s│
│  Nav2's plan (yellow)                                                    │ wheels  OK   │
│                                                                          │ ARMED  COMP  │
│                                                                          │ steer +0.12  │
│                                                                          │ tracker: lqr │
└──────────────────────────────────────────────────────────────────────────┴──────────────┘
```

| Layer | From | Frame |
|---|---|---|
| Cubes | `/sensors/lidar/points` (reliable, keep last 1) | lidar_link → base_link → odom |
| EKF local | `/localization/odom/local` | odom |
| EKF global, AMCL, truth, plan | their topics (AMCL's: `/localization/amcl/pose`) | map, drawn through map → odom |
| Panel | each sensor's own topic, `/vehicle/status`, `/drivers/nav/track/status` | - |

**Later, in this order:** cubes that persist and fade; AMCL's particles (best effort);
the live tracker swap from the keyboard; NDT (its own design, `2026-10-29_ndt.md`); objects
(from perception, not the viewer).

## Frames and timing (the review's main finding)

| Rule | Why |
|---|---|
| Read `/tf` and `/tf_static` (`tf2_msgs/TFMessage`): keep the latest `map → odom` and the static `base_link → lidar_link` | rclrs has no tf2 buffer, but the messages are plain; map-frame layers would drift from the cubes without `map → odom` |
| Place each cloud with the **local EKF's pose at the cloud's stamp**: keep 1 s of poses, interpolate; drop a cloud outside it | the cloud arrives late; at 3 m/s a 50 ms mismatch doubles walls 20 m away |
| Compare stamps only with stamps, never with the node's clock | Gazebo stamps sim time; the HUD runs on wall time |
| Ignore the VLP-16's 0.1 s sweep (Gazebo's lidar has none); say so | v1 |
| Heights are above `base_link` (2D EKF: no roll or pitch); say so | a pitched car tilts the cubes |

## Where the code lives

| Part | Where | Reused from |
|---|---|---|
| The cube grid (one `HashSet` of cube indices per scan), height colours, the pose buffer and its interpolation | `crates/debug-core` (new): no ROS, no raylib, tested | - |
| Reading the cloud (x, y, z by name, FLOAT32, endianness, `point_step`/`row_step`, skip non-finite; Gazebo's organised and the VLP-16's unorganised clouds) | shared | `aav_radar_clusters`' `radar-clustering` `cloud.rs` (path dependency, or moved to a small shared crate) |
| Car outline, poses, quaternions | `map-core` | `CarShape::from_vehicle_yaml`, `geom::Pose` |
| Panel health, vehicle status | `hud-core` | `health::LastSeen`, `vehicle::VehicleStatus` |
| The window and the node | `crates/debug-app` (new), binary `debug_hud` | `hud-app` `window.rs` and its ROS-thread channel pattern |
| Topic names, stale times, cube size | `config/debug_hud.yaml` | the `hud.yaml` / `map.yaml` pattern: no topic names in Rust |

**The cloud never goes through the shared update queue:** a newest-only slot (one cloud at
most), parsed and turned into cubes off the drawing thread; the screen gets only the cubes.

**Drawing:** one cube mesh, drawn instanced (`draw_mesh_instanced`, OpenGL 3.3 on macOS),
colour per instance. Pass/fail in step 2: 20,000 cubes at 30 fps or more, release build,
on a team Mac. Above a cap, the nearest cubes are kept, and the panel says some were cut.

`package.xml` gains `tf2_msgs`, `nav2_msgs`, `diagnostic_msgs`, `rcl_interfaces` (their Rust
code is in the pixi env).

## Swapping trackers live (later step, sim only)

| Part | Rule |
|---|---|
| `aav_track` | `live_swap` parameter, default **false**; `sim.launch.py` sets it true. A parameter callback builds the new tracker between ticks (the node is single-threaded), declares every tracker's parameters at start, keeps the path's hint (`tracker.hint = job.hint`), seeds its steering estimate from the wheels' angle, resets the loop statistics, logs the swap |
| First use | from a terminal: `ros2 param set /track tracker lqr`; the panel shows it from the status topic |
| Keys 1-4 (later) | the debug HUD calls `/track/set_parameters`, only when `/system/source` says SIM; shows the reply's reason |
| D3 | the debug HUD never touches an actuator; it may retune a **sim** tracker |

## `pixi run debugdemo`

`tools/demo_all.sh debug [fullscreen]`: `pixi run demo` (Gazebo's walled test lot, the nav
screen, the street-map window, **and the in-car HUD**, which keeps the on-screen e-stop),
plus `debug_hud`, with `amcl:=true tracker:=pure_pursuit reversing:=false` (the test lot's
defaults already have nav and the lidar on, as `amcl:=true` needs). Local only: it joins
`tools/test.sh`'s list of stand-in tasks; a row in README.md's "Every command".

## On the car

For now: Gazebo, and the Orin's own screen. A Mac on the car's WiFi would pull ~9 MB/s of
reliable lidar (the Foxglove bridge already leaves it out). Later: a small cube topic
published on the car, into `interfaces.yaml` first.

## Order

1. Thin slice: `debug-core` grid + pose buffer; `debug_hud` with cubes, car, EKF local; `debugdemo`.
2. map → odom from `/tf`; EKF global, truth, AMCL pose, plan; the drawing test (20,000 cubes).
3. The panel.
4. `aav_track` live swap (terminal), then keys 1-4.
5. Persisting, fading cubes; AMCL particles; NDT layer (after the NDT design). Built 29 Oct (B10-B17).

## Built (29 Oct): steps 1-4, and the choices made

| # | Choice | Why |
|---|---|---|
| B1 | Cubes coloured in one cool ramp (dark ground, teal, pale tops) | the localizers' blue, green, white and orange stay readable on top |
| B2 | One instanced draw per height band, with a small GLSL 330 shader (face shade by normal) | raylib's DrawMeshInstanced has no per-instance colour; six bands = six draws |
| B3 | The 3D view gets its own viewport and projection; the panel is 2D beside it | the car stays centred in the view, not under the panel |
| B4 | Camera: CHASE (behind the car), FOLLOW, FREE; `C` switches, `R` resets | behind the car reads like the windscreen; a drag frees it |
| B5 | Gazebo's truth isn't frame-checked; the other poses are (odom, map) | the truth's frame is Gazebo's world name, which is map by construction |
| B6 | The cubes thread waits up to 0.3 s for the pose at a cloud's stamp; a newer cloud wins | the EKF's pose can land a little after the cloud |
| B7 | A live swap seeds lqr's and mpc's steering estimate with the last command, not the wheels' measured angle | the track node doesn't read the wheels; adding it would need a new subscription |
| B8 | Keys 1-4 call `/track/set_parameters` only when every sensor in `/system/source` is SIM | D3: never the car; the node refuses too without `live_swap` |
| B9 | `--demo` ray-casts a 16-beam lidar in a walled lot; `--bench-cubes N` is the drawing test | both run with no ROS, on any laptop |

## Built (29 Oct): step 5, and the choices made

| # | Choice | Why |
|---|---|---|
| B10 | Kept cubes are the default view; **K** swaps to this scan's | the "occupancy network" look is what Ben asked to see |
| B11 | A kept cube fades in 4 steps over `keep_cubes_for` (2 s), aged by the clouds' stamps, then goes; over `max_cubes` the nearest are drawn | stamps, not the clock (sim time); 4 steps = 24 instanced draws, not one colour per cube |
| B12 | Fading is drawn **darker** (towards the background), not see-through | opaque cubes need no sorting; see-through ones would flicker |
| B13 | NDT is a fifth localizer, purple, with its own panel section: TRACKING / WAITING / LOST, score per point, ms per match, overlap, restarts | its pose comes only on good fits, so the section shows why when it stops |
| B14 | NDT's map: the PCD (`ndt_map`, read once with ndt-core's own reader), 1 m cells with 3 points or more, faint purple wireframes through map -> odom; **M** toggles; on when the file loads | see the scan sitting on the map; a stray point isn't a wall |
| B15 | No map: the panel says where it looked and `pixi run ndt-map drive`; `debugdemo` adds `ndt:=true` only when `maps/ndt/test_lot.pcd` is there | sim.launch.py refuses `ndt:=true` without the file |
| B16 | AMCL's particles: small orange arrows on the ground (best effort), at most 5,000; **A** toggles | AMCL's own max is 2,000 |
| B17 | A key legend, bottom left, with each layer's state; **H** hides it | one list (debug-core `keys`) for the legend, the keys and `--help` |
